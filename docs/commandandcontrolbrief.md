# Goal
Build a browser prototype of the Command & Control page from three components: `RbmCommandCentre` (page template), `RbmEventBar` (sticky compact bar) and the Layout panel. Everything is fed by JSON through the same data model the real ServiceNow data will use later. There are no network calls and no back end.

# 1. Data contract first (stop and show me before building on it)
- Write TypeScript types in `src/data/types.ts` for: event, runbook (id like RBK0000001), stage, task (WBS id, state, planned and forecast start and end, dependencies, constraints, assignee, tags such as late to start, late to finish, has an issue), alert, blocker, issue, milestone, next checkpoint (with optional linked call), and the forecast (forecast end, planned end, RAG, minutes behind or ahead).
- Define a `CommandCentreData` interface (read data, subscribe to changes) and a `LayoutPreferenceStore` interface (get, set, reset). Implementations are swapped later. The template must never know where data came from.
- Document the types and the fake-engine rules in `docs/data-model.md`. Wait for my review of the contract before you build components on it.

# 2. Fixtures (JSON, validated against the types, so a mismatched file fails the build)
- `weekend-payroll-cutover`: the example on the Command board (3 runbooks, 124 tasks, forecast +12 min, 2 blockers, 5 issues).
- `healthy-event`: on schedule, no alerts, so the alert counter is hidden.
- `badly-late-event`: Red forecast, several blockers, a failed check.
- `large-event`: about 15,000 tasks across many runbooks and stages, with overlapping stages, generated by a script (`npm run fixtures`) with a fixed seed. Do not commit hand-written 15,000-task JSON.
- Add a fixture switcher to the demo app.

# 3. Fake engine (clearly labelled as a stand-in for the RBM planning engine)
- A small, pure, unit-tested module. Dependencies and constraints decide which tasks are Ready or Up next (an Up next cap of 5 released tasks is applied by the Task Timeline, not the engine).
- Start and Complete change a task's state and recompute: successor tasks released, forecast end (critical path), RAG against planned end, late flags and the alert list. Completing is undoable for the 60 s linger.
- Pause, Skip, and bulk Start and Complete work the same way.
- The clock is injectable and can be sped up. Linger time, countdown to the next checkpoint and the "now" line follow it.
- Keep the rules simple and documented. They are not the real engine, and must be easy to delete.

# 4. Components
- **`RbmCommandCentre`:** fixed Page header and Event vitals at the top (slots). Then the Event ribbon, Task Timeline and Hot-topics strip as movable regions in the saved order. Default order: ribbon, Task Timeline, strip. Task Timeline keeps a minimum of 8 rows. The ribbon can be collapsed to a 56 px summary line (open by default, remembered). The regions arrive as slots. Where a real component does not exist yet, use a simple stand-in that reads the same data and shows real values, so the page can be exercised now and swapped later without changing the template.
- **`RbmEventBar`:** 48 px, appears when the Event vitals leave the viewport (IntersectionObserver) and disappears when they return, so the same facts are never shown twice. Shows event name and state, alert counter, progress, open issues, Forecast end time with its RAG disc and words. Fixed regardless of layout order. The Task Timeline toolbar sticks beneath it.
- **Layout panel:** opened from a "Layout" row in the event actions menu. Page header and Event vitals are shown locked ("FIXED"). The three movable regions drag by their grip using dnd-kit, with full keyboard support (Space picks up, arrow keys move, Space drops) and screen-reader announcements. Reset to default and Done. The order is saved through `LayoutPreferenceStore` (localStorage in the prototype) and survives a reload.
- Use the tokens, theme and `RbmStatusPill` already in the repo. Row action buttons are 120 by 32 px (see the brief).

# 5. Demo app
A small Vite app in this repository, with a route for the whole page, the fixture switcher, a clock-speed control and a reset. It must run with `npm run demo`.

# 6. Acceptance
- Stories for each component and for the whole page.
- Tests for: layout order logic (default, change, reset, reload), the bar appearing and disappearing at the scroll threshold, keyboard dragging, the fake engine rules, and fixtures validating against the types.
- The page works at 1080 px, 1440 px and a wall display. With the large event it stays responsive (virtualise the Task Timeline).
- Colour is never the only signal. The alert counter is Red, Amber or hidden as in the brief.
- Anything that differs from the design is flagged in `claude/rbm-parked-decisions.md` and listed at the end of your report.
